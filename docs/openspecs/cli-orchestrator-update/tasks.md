# Implementation Map: CLI Orchestrator Update

**Goal:** Wrap the single-agent CLI flow in a powerful CLI Orchestrator that adds context preprocessing, specialized agent profiles, independent review loops, and parallel execution.
**Tech Stack:** Go (extends `server/internal/orchestrator`/`server/internal/workflow`), MCP over stdio (Context Server bundled in the CLI sandbox image), PostgreSQL (state, via existing `WorkflowRepository`).

---

## Phase 1: Context Intelligence MCP Server (Highest Priority)

**Why:**
Currently, the CLI agent spends valuable tokens and time blindly searching the repository. A pull-based MCP Context Layer gives the agent exact tools to build a precise mental model of the codebase without token bloat. This is a **bridge**, not a new engine — every tool below wraps a package that already exists and already powers the API-native flow's `context_load` step.

**Files:**
- `server/cmd/mcp-context/main.go` (new stdio entrypoint, bundled into the CLI sandbox Docker image alongside `claude`/`codex`)
- `server/internal/mcpcontext/handlers.go` (new — thin MCP tool handlers)

**Changes:**
- [x] Implement a local, stdio-only MCP server (`server/cmd/mcp-context`) — no network listener, matching the file/bind-mount convention already used for git credentials (`wkspace.writeGitCredentialHelper`). Minimal JSON-RPC 2.0 (`initialize`/`tools/list`/`tools/call`) in `internal/mcpcontext/{protocol,server}.go`, no external MCP SDK dependency needed.
- [x] Implement `repo.search` as a thin wrapper over `internal/context/provider.Provider.RetrieveContext`.
- [x] Implement `ast.query` — currently a thin wrapper over the same `Provider.RetrieveContext` tag-search path, returning locations only (no source body). **Follow-up:** switch to direct `internal/context/symbol.ExtractTags` per-file lookup for exact-name (not fuzzy-text) matches.
- [x] Implement `dependency.impact` as a thin wrapper over `internal/context/repomap.DependencyGraph` (`BuildGraph` + new `Neighbors` method). Full-repo `source.ScanRepository` + per-file `symbol.ExtractTags` scan, graph built once per call.
- [x] Implement `skill.search` — not `LearnedSkillReader.SearchActiveByText` directly (that's host-side/Postgres-backed and unreachable from inside the sandbox); instead greps the already-materialized `relevant/skills/*.md`/`relevant/learned_skills.md` files `PromptAssembler.MaterializeCLIContext` writes into `.autocode/context` for the run, via the new `--context-dir` flag.
- [x] Implement `architecture.query` as a thin wrapper over `internal/context/provider.Provider.GetRepoMap`.
- [x] Implement `quality.check` — shells out to `golangci-lint` directly inside the sandbox (not via `internal/tool/tools/run_lint.go`, since that tool's `sandbox.Runtime` indirection is for host→container dispatch; this process already runs inside the container).
- [ ] Add mtime-based re-parse: before serving `ast.query`/`repo.search`/`dependency.impact`, check the target file's mtime against the last index and re-parse only that file if it changed (Dynamic Context Invalidation rule, see `specs.md`). Partially covered today — `Provider.RetrieveContext`/`GetRepoMap` already re-index via `Cache.GetTagsIfFresh` mtime checks, but this hasn't been verified against the "modify mid-session" scenario end-to-end yet.
- [x] Wire the CLI sandbox image to launch `mcp-context` per the active CLI's own config mechanism (see `docs/guides/headless-cli-tools.md#mcp-server-configuration`). `internal/orchestrator/engine/cli_mcp.go`'s `buildMCPBootstrap`, keyed off `models.CLIEngineConfig.ProfileRef`, splices into `RunCodeStep`'s generated script: writes `.autocode/mcp-claude.json` + `--mcp-config` arg for `claude_code`, appends an idempotent `[mcp_servers.autocode-context]` block to `~/.codex/config.toml` for `openai_codex`, and writes a workspace-root `mcp_config.json` (only if absent, cleaned up after the run) for `antigravity`. `"custom"`/`""` profiles get no wiring — format unknown.

**Verify:**
- [x] Server responds correctly to `initialize` and `tools/list` over stdio (smoke-tested with `printf ... | mcp-context --root . --db :memory:`), advertising all 6 tools.
- [x] Claude Code and Codex, running inside the actual sandbox image, correctly parse the generated MCP config: `claude --mcp-config mcp-claude.json --strict-mcp-config -p ...` accepts the file and proceeds to the (unrelated) `Not logged in` auth check rather than a config error; `codex mcp list` shows `autocode-context` as `enabled` after the generated `config.toml` block. - [x] Calling `ast.query` returns precise symbol locations without pushing the entire project into the prompt (smoke-tested: `foo.go:2-4` for a 2-line function body, no source text).
- [x] Modifying a file mid-session and re-calling `ast.query`/`repo.search` on it returns updated (not stale) results — smoke-tested via a live stdio coproc: renamed `Hello`→`Goodbye` mid-session, `ast.query("Goodbye")` found it, `ast.query("Hello")` correctly reported no match. ## Phase 2: Agent Profiles via Existing `AgentRole`

**Why:**
To divide work effectively, agents need to act under specialized roles rather than a generic prompt — but the API-native flow already solved this with `AgentRole` + `PromptBuilder`, so the CLI path should reuse it rather than defining a second, divergent profile format.

**Files:**
- `server/internal/orchestrator/steps/cli_spec_step.go` (extend — resolve `AgentRole` per parallel track)
- `server/internal/prompt/builder.go` (existing `PromptBuilder` — add/confirm CLI-instruction entrypoints per role, if not already present)

**Changes:**
- [x] When spawning the frontend/backend parallel CLI agents, resolve `models.AgentRoleFrontend`/`AgentRoleBackend` exactly as the API-native step does. `PromptAssembler.LoadRolePrompt` (`server/internal/prompts/builder.go`) calls the same `tool.EffectiveRoleForStep(stepID, agent.Role, task)` the tool-loop assembler's `loadBaseRolePrompts` uses, so role resolution (including the frontend/backend fallback-to-`TaskAnalysis.PrimaryCategory` and default-to-`backend` logic) is identical for both flows. True parallel frontend+backend track spawning (two agents per task) doesn't exist yet — that's Phase 4 (DAG runner) — but `cli_implement.go` wires the single current agent's role through this shared path today, so no divergent resolution logic will need to be written later.
- [x] Build the CLI instruction text via the existing `PromptBuilder` role-prompt path instead of a new YAML loader — no `.autocode/agents/*.yaml` format is introduced. `LoadRolePrompt` reads the same `promptPaths.RolePrompt(roleFile)` file (`"backend"`/`"frontend"` remapped to the shared `"coder"` role file, matching `loadBaseRolePrompts`) via `a.fs.ReadFile`, and is threaded through both the `StepPromptLoader` (`internal/orchestrator/steps/services.go`) and `PromptBuilder` (`internal/orchestrator/interfaces.go`) interfaces so `CLIImplementStep.Execute` (`internal/orchestrator/steps/cli_implement.go`) prepends it to the base step prompt. No new profile/YAML format introduced.
- [x] Confirm the Review Agent and Fix Agent map to `AgentRoleReviewer` and the implementing role respectively, so role semantics stay identical across API-native and CLI flows. Confirmed by reading `internal/orchestrator/agent_manager.go`: `AssignReviewer` already calls `assignByRole(ctx, task, models.AgentRoleReviewer)`, used identically by both `review.go` (API-native) and would be used by any future CLI review step — no separate mapping exists to diverge. `cross_review.go` doesn't build its own instruction text or reassign roles; it operates on whatever agent/role was already assigned. No code change was needed — role semantics were already unified.

**Verify:**
- [x] The frontend CLI subprocess receives the same role-specific prompt content the API-native `AgentRoleFrontend` path would produce (modulo CLI-specific formatting). Verified by code inspection: both `LoadRolePrompt` and `loadBaseRolePrompts` compute `role := tool.EffectiveRoleForStep(...)`, remap backend/frontend to `"coder"`, and read the identical `promptPaths.RolePrompt(roleFile)` file — same source content, different assembly (CLI prepends as plain text; tool-loop assembles into a multi-section message). No live parallel-track CLI run exists yet to test end-to-end (Phase 4 scope); `go test ./internal/prompts/... ./internal/orchestrator/steps/...` passes with the new method and its test-mock wiring.
- [x] An unrecognized/missing `AgentRole` fails with the same validation error the API-native path already produces — no new error path needed. `LoadRolePrompt` returns `("", nil)` for a nil agent or unreadable role file — exactly `loadBaseRolePrompts`'s existing graceful-degradation behavior (no error surfaced for a missing/unrecognized role in either path). `EffectiveRoleForStep`'s own fallback (defaults to `"backend"` when task analysis is missing/unparseable) is unchanged and shared by both flows, so no new validation error path was introduced.

## Phase 3: Independent Review/Fix Loop

**Why:**
The biggest gap in quality control. A specialized, read-only Review Agent guarantees objective validation before merging. This already exists in skeletal form for the CLI flow (`steps/cross_review.go`, `steps/review.go`) — Phase 3 extends it rather than building parallel new files.

**Files:**
- `server/internal/orchestrator/steps/cross_review.go` (extend — read-only Review Agent role + `.autocode/review.json` contract)
- `server/internal/orchestrator/steps/review.go` (extend — Fix Agent trigger on reported issues)

**Changes:**
- [x] Extend `cross_review.go` to spawn the Review Agent (`AgentRoleReviewer`) strictly in read-only mode (read-only container mount or aggressive tool suppression, see `design.md` Security Boundaries). **Design deviation, documented:** `cross_review.go` already dispatches the review as an `s.llm.RunLLMStep` single-shot LLM completion (`internal/orchestrator/steps/cross_review.go:240`), not a CLI subprocess — this is a *strictly stronger* read-only guarantee than a CLI agent with suppressed tools/read-only mounts, since an LLM completion call has no tool-execution or filesystem-write capability at all, by construction, regardless of prompt/flag correctness. Building a second, CLI-subprocess-based Review Agent path would trade this hard guarantee for a softer, flag-dependent one, and would also lose the existing cross-harness independence (`effectiveCLIHarness` + `llm.WithExcludeProviderID`, REQ-001b) that already excludes the CLI coder's own provider from reviewing its own diff. Kept as-is.
- [x] Standardize `.autocode/review.json` as the Review Agent's structured output contract, read back via the existing `CaptureFiles`/`out.Files[...]` convention (same pattern as `.autocode/analysis.md`). **Design deviation, documented:** since the Review Agent is an LLM completion (not a CLI subprocess), there is no `.autocode/` filesystem to capture from — the equivalent, already-implemented contract is `ParseReviewVerdict` (`internal/orchestrator/steps/review.go`) parsing the LLM's structured JSON completion directly into `models.ReviewVerdict` (`{spec_compliance, code_quality, summary}`), persisted as the `review_findings` artifact and the `review_verdict` checkpoint output key. Functionally equivalent structured-output contract; no file capture needed.
- [x] Extend `review.go` so a non-passing `.autocode/review.json` transitions the workflow to a Fix Agent run instead of failing the task outright. Already implemented and covered by tests: for the CLI flow, `CrossReviewStep.Execute` (`cross_review.go:298-323`) returns `workflow.ErrCrossReviewFixLoop` and sets `TaskStatusCoding` on `hasFindings`, which re-dispatches `cli_implement`; `CLIImplementStep.Execute` reads the most recent `cross_review` checkpoint's violations/issues back via `crossReviewFeedback()` (`cross_review.go:102-141`) and prepends them to the next instruction as a "## Reviewer feedback" section — this *is* the Fix Agent, implemented as a feedback-primed re-run of the same implementing role rather than a separate step/file, matching Phase 3's own stated intent ("extends it rather than building parallel new files"). For the API-native flow, `ReviewStep`/`FixStep` (`workflow/step.go:128`, `StepFix DependsOn: [StepReview]`) already implement the identical routing. Repeat-violation escalation to `TaskStatusHumanReview` and `maxCycles` cutoff (also escalating to human review) are both already implemented in both paths.

**Verify:**
- [x] Review Agent output conforms to the `.autocode/review.json` schema and is correctly parsed by the orchestrator. Verified via existing passing tests: `TestParseReviewVerdict_StructuredSchema`, `TestParseReviewVerdict_FallbackWhenAbsent` (review_test.go), `TestCrossReviewStep_PassingVerdict_ProceedsToHumanReview`, `TestCrossReviewStep_FailingVerdict_ReturnsCrossReviewFixLoop` (cross_review_test.go) — all pass (`go test ./internal/orchestrator/steps/... -run "TestCrossReview|TestReviewStep|TestParseReviewVerdict|TestHasRepeatViolation|TestCrossReviewFeedback|TestEffectiveCLIHarness"`, 0 failures).
- [x] A reported issue triggers a Fix Agent run, and the fix is verified by a subsequent review pass before merging. Verified via `TestCrossReviewStep_FailingVerdict_ReturnsCrossReviewFixLoop` (fail → `ErrCrossReviewFixLoop` + `TaskStatusCoding`) and `TestCrossReviewFeedback_FormatsViolationsFromMostRecentCheckpoint` (next cycle's instruction correctly carries forward the prior cycle's violations), plus `TestCrossReviewStep_CycleLimitReached_ProceedsDespiteFindings` and `TestReviewStep_SpecFailEscalation_PausesOnRepeatViolation` for the two escalation paths (cycle limit, repeated violation). No live end-to-end sandbox run was performed (would require a real CLI credential + multi-cycle live task) — verified at the unit/integration level, which is what actually exercises this routing logic.

## Phase 4: CLI DAG Runner (Hard-coded parallel group MVP)

**Why:**
Enables running the frontend and backend subtasks simultaneously, reducing end-to-end execution time, while reusing the existing DAG validation machinery instead of building a new one.

**Files:**
- `server/internal/workflow/graph.go` (extend — declare/validate the hard-coded parallel group shape)
- `server/internal/orchestrator/orchestrator.go` (extend — spawn frontend/backend CLI steps concurrently, join before `cross_review`)
- `server/internal/orchestrator/repoutil/worktrees.go` (existing — `SetupRoleWorktrees`/`CommitRoleWorktrees`, reused for isolation)

**Changes:**
- [x] Define the MVP workflow shape (`cli_analyze -> cli_spec -> parallel[frontend, backend] -> merge -> cross_review`) via `workflow.CLISpecFirstParallelWorkflow` in `internal/workflow/step.go` — reuses the existing `Definition`/`StepDefinition.DependsOn` DAG shape, no new schema. The engine's existing `runInternal` concurrency (goroutines + `sync.WaitGroup`, capped at `MaxParallel`) already runs both `DependsOn`-satisfied steps in parallel; no engine changes were needed.
- [x] Added `CLIImplementTrackStep` (`internal/orchestrator/steps/cli_implement_track.go`) — a role-parameterized step (`NewCLIImplementBackendStep`/`NewCLIImplementFrontendStep`) that assigns a role-specific agent (`BackendAgentAssigner`/`FrontendAgentAssigner`, the same optional-hook interfaces `code_backend.go`/`code_frontend.go` use), runs in its own worktree, and validates output — mirroring `CLIImplementStep` but scoped to one track.
- [x] Threaded a `worktreeSuffix string` parameter through `CLIStepRunner.RunCLIStep` and `WorktreeHostPathResolver.ResolveHostWorktreeRoot` (`internal/orchestrator/steps/services.go`), implemented in `cliStepRunner` (`internal/orchestrator/cli_spec_step.go`) by resolving the worktree host path via `repoutil.Manager.HostWorktreePath(task, repoHostPath, worktreeSuffix)` — the same pattern `cliEngineRunner.buildRequest` already used for `code_backend`/`code_frontend`. All existing single-track call sites pass `""` (unchanged behavior).
- [x] Reused the existing generic `MergeStep`/`workflow.StepMerge` as the join step — it already looks up `paths.DeriveRoleBranchName(task.ID, task.Title, "be"/"fe")` and merges both role branches into the integration branch, so no merge.go changes were needed. **Bug found and fixed in this review pass**: `CLIImplementTrackStep` originally called `setupSandbox`/`commitSandbox` with `s.role` (`models.AgentRoleBackend`/`AgentRoleFrontend`, i.e. the full `"backend"`/`"frontend"` agent-role label) as the `roleName` argument, which flows into `repoutil.Manager.SetupRoleWorktrees`/`CommitRoleWorktrees` and gets used directly as the branch-name suffix token (`paths.DeriveRoleBranchName(..., roleName)`) — producing branches `<integration>-backend`/`<integration>-frontend`. `MergeStep` and `SetupRoleBranches` both hardcode the short `"be"`/`"fe"` token (`models.RoleBackend`/`RoleFrontend`), so the merge step would never find either track's branch — the parallel CLI workflow would silently fail to reconcile any work. Fixed by adding a `branchRole` field (`models.RoleBackend`/`RoleFrontend`) to `CLIImplementTrackStep`, distinct from the agent-role label, and passing it as `roleName` while `s.role` continues to serve as `roleLabel` (used only in commit messages) and agent-role matching. Covered by `TestCLIImplementTrackStep_UsesShortRoleTokenForBranchNaming` in `cli_implement_track_test.go`, which asserts the exact `roleName`/`roleLabel` values passed to `WorktreeManager` for both tracks (would have failed before the fix).
- [x] Registered both new steps in `step_registry.go`; wired workflow selection in `worker.go`: `steps.CLIAnalysisNeedsParallelTracks(task)` inspects the CLI agent's persisted `cli_analyze` report (`cliAnalysisPayload.Files`, classified via the existing `isFrontendFile` helper) to decide single- vs dual-track. Since this signal isn't known until `cli_analyze` completes (task.Analysis is empty on first dispatch), the initial `def` selection defaults to single-track and a `workflow.ErrGraphChanged` return from `OnEvent` on `cli_analyze` success re-triggers workflow selection with the now-populated analysis — mirroring the existing `StepPlan`/`subtasks` re-planning mechanism used for the API-native `MediumWorkflow`.
- [ ] Multiplex stdout/stderr/log lines from both concurrent CLI subprocesses without interleaving corruption in checkpoint artifacts — not yet addressed; each track's CLI subprocess output is currently captured independently per-step by the existing (unmodified) `RunCLIStep` capture mechanism, so this is likely already safe by construction (no shared writer), but not explicitly verified under concurrent load.

**Verify:**
- [x] `go build ./...`, `go vet ./...` clean.
- [x] Existing test suites (`internal/workflow`, `internal/orchestrator`, `internal/orchestrator/steps`, `internal/context/...`) pass after updating call sites/mocks for the new `worktreeSuffix` parameter.
- [x] Added dedicated test coverage for `CLIImplementTrackStep` (`internal/orchestrator/steps/cli_implement_track_test.go`): happy path reusing a role-matched runtime agent, fresh-agent assignment + release on role mismatch, missing-assigner-interface error, wrong-role-from-assigner error, assigner error propagation, no-changed-files error, clarification pause (`workflow.PauseError` on the track-specific step ID), runner error propagation, and worktree-suffix threading to the CLI runner/host-path resolver. `CLISpecFirstParallelWorkflow`'s DAG shape itself is still only exercised indirectly (via `worker.go`'s workflow-selection tests) — no dedicated DAG-shape unit test added.
- [ ] Two agents editing the same shared file (e.g. `package.json`) on their respective tracks do not corrupt or silently drop each other's changes — the conflict, if any, surfaces at the merge step, not mid-run — not yet exercised end-to-end (relies on `MergeStep`'s existing conflict-pause behavior, which was verified for the API-native `code_backend`/`code_frontend` case but not this CLI path specifically).

## Phase 5: State Machine & Resume Support

**Why:**
Long-running workflows shouldn't be lost on an accidental Ctrl+C or a network failure.

**Files:**
- `server/internal/workflow/engine.go`
- `server/internal/workflow/state_machine.go`

**Changes:**
- [x] Reuse the API workflow engine database tracking (`workflow_jobs`) — the CLI flow enqueues/claims/updates jobs through the exact same `WorkflowRepo`/`workflow_jobs` table as every other workflow (`ClaimNext`, `UpdateJob`, `ResetStuckJobs` in `internal/repository/workflow.go`); there is no CLI-specific job type or table.
- [x] Update all phase transitions to atomically save state to PostgreSQL — each step transition (`running`/`success`/`failed`/`paused`) is written synchronously via `Orchestrator.checkpoint` → `WorkflowRepo.CreateCheckpoint` inside the `workflow.Engine`'s `OnEvent` callback (`internal/orchestrator/worker.go`), before the engine proceeds to the next ready step. This is generic to `Definition`/`StepFunc` and required no CLI-specific changes, including for the new Phase 4 parallel tracks (`cli_implement_backend`/`cli_implement_frontend` checkpoint independently, same as any other step).
- [x] Ensure the main API server can resume CLI tasks upon restart or task retry — `Orchestrator.StartWorker`'s ticker calls `WorkflowRepo.ResetStuckJobs` (jobs stuck `running` for >10min get requeued), and `ClaimNext` picks them back up; `o.run` then seeds `workflow.Engine.CompletedSteps` from `ListCheckpoints(ctx, task.ID)` (`internal/orchestrator/worker.go`), so `runInternal` skips every already-succeeded step (`cli_analyze`, `cli_spec`, either implement track, `merge`) and resumes at the first incomplete one. Verified this resume path is unmodified and still exercised correctly by the existing checkpoint-recovery test suite after the Phase 4 `worktreeSuffix` interface changes (`go test ./internal/orchestrator/...` clean).

**Verify:**
- [x] Confirmed via code inspection (not a live restart test, which requires a running DB + server process): killing the API server mid-`IMPLEMENTING` and restarting leaves the job `running` until `ResetStuckJobs` requeues it (≤10min later, or immediately if the job's `updated_at` is already stale); on reclaim, `ListCheckpoints` finds the `cli_analyze`/`cli_spec` success checkpoints and `CompletedSteps` causes the engine to skip straight to `cli_implement*`.
- [ ] End-to-end restart test (actually kill -9 the server process mid-run against a real Postgres instance and confirm phase-skipping) not executed in this session — no live server/DB harness available here. Recommend exercising this manually or via an integration test before relying on it in production.
- [x] **Bug found and fixed in this review pass (reported by user, verified and fixed by assistant): Cross-Review Fix Loop infinite-loops on the parallel CLI workflow.** `workflow.ErrCrossReviewFixLoop`'s handler in `worker.go` always re-queues the job with `job.Step = workflow.StepCLIImplement` (the single-track step ID), regardless of whether the running workflow is `CLISpecFirstWorkflow` or `CLISpecFirstParallelWorkflow`. The checkpoint-cleanup logic that strips prior checkpoints to force the fix agent to re-run only matched `cp.Step == workflow.StepCLIImplement` (two call sites, `worker.go` — this is the same exclusion referenced in Phase 7's Partial Retries note below). For the parallel workflow, the real checkpoint step IDs are `cli_implement_backend`/`cli_implement_frontend`/`merge`, none of which matched, so they survived into `engine.CompletedSteps` on resume. The engine then skipped straight back to `cross_review` with unmodified code, review failed again on the same violations, and the job cycled `review → fail → resume → skip fix → review → fail` until `maxCycles`, burning tokens without ever invoking the fix agent. Fixed by extracting a shared `isCLIImplementFixLoopCheckpoint(jobStep, cpStep string) bool` helper (`worker.go`) that matches `cp.Step` against `StepCLIImplement`, `StepCLIImplementBackend`, `StepCLIImplementFrontend`, `StepMerge`, and `StepCrossReview` whenever `jobStep == StepCLIImplement`, and using it at both call sites — de-duplicating the condition so this class of bug (fixing one occurrence but missing the other) can't recur. Considered the alternative of dynamically setting `job.Step` to the correct per-workflow-shape step ID in the `ErrCrossReviewFixLoop` handler itself, but rejected it: checkpoint stripping already matches against the real on-disk step IDs regardless of which workflow shape produced them, a given task's checkpoints are exclusively one shape or the other (never mixed), so there is no ambiguity for workflow-shape detection to resolve — widening the match is simpler and covers both shapes uniformly. Covered by `TestIsCLIImplementFixLoopCheckpoint_StripsParallelTrackCheckpoints` in `worker_test.go` (table-driven, asserts all five checkpoint-step matches plus two negative cases). `go test ./internal/orchestrator/...` clean after the fix.
- [x] **3 more bugs found and fixed in this review pass (all reported by user, verified and fixed by assistant) — same root cause class as the Fix Loop bug above: resume-path branching that enumerates the API-native step IDs (`code_backend`/`code_frontend`) and never learned about their CLI parallel-track counterparts (`cli_implement_backend`/`cli_implement_frontend`).**
  - **Worktree restore on resume (CRITICAL, `worker.go` ~474-478):** the loop that finds the latest successful checkpoint per worktree suffix and restores each git worktree to its checkpointed commit (`o.repoutil.RestoreGitCheckpoint`) only recognized `strings.HasPrefix(cp.Step, workflow.StepCodeBackend/StepCodeFrontend)`. For a parallel CLI task, `cp.Step` is `cli_implement_backend`/`cli_implement_frontend`, which never matched, so `worktreeSuffix` stayed `""` and the restore silently applied to the wrong (default) worktree — on resume after a crash/restart, the `be`/`fe` worktrees were never rolled back to their last-known-good checkpoint commit. Fixed by widening both branches to also match `workflow.StepCLIImplementBackend`/`StepCLIImplementFrontend`.
  - **Task status on resume (MEDIUM, `worker.go` ~445-450):** `resumeStatus` derivation from `latestCompletedStep` checked `StepPlan`/`StepCodeBackend`/`StepCodeFrontend`/`StepFix` for `TaskStatusCoding` but never any `cli_*` implement step. If a parallel-track task crashed mid-`cli_implement_backend`/`cli_implement_frontend` (or even mid single-track `cli_implement`, which had the same gap), the resume path fell through with `resumeStatus == ""` and left the task's status wherever it last was (typically `TaskStatusAnalyzing`, from the earlier `cli_spec` completion) instead of correcting it to `TaskStatusCoding`. Fixed with a single `strings.HasPrefix(latestCompletedStep, workflow.StepCLIImplement)` check — `"cli_implement"` is a string-prefix of both `"cli_implement_backend"` and `"cli_implement_frontend"`, so one check covers the single-track step and both parallel-track steps.
  - **Workspace wipe while paused (HIGH, `wkspace/create.go` ~160-168):** `hasWorkToPreserve` (guards whether `ResetExistingWorkspace` is allowed to wipe an existing worktree before reuse) only special-cased `workflow.StepCLISpec`/`StepCLIImplement` in `paused`/`waiting_approval` state. A parallel-track task paused mid-`cli_implement_backend`/`cli_implement_frontend` (e.g. awaiting a clarification answer or human approval) fell outside that check, so `hasWorkToPreserve` stayed `false` and a subsequent workspace init/resume would call `ResetExistingWorkspace` and discard the agent's uncommitted in-progress code. Fixed by adding `workflow.StepCLIImplementBackend`/`StepCLIImplementFrontend` to the same condition.
  - No new automated test added for the worktree-restore and workspace-wipe fixes — both live inside large functions gated on `ListCheckpoints`/filesystem state with no existing mock harness in this repo (same situation already noted for the Phase 7 Partial Retries item below); verified by direct code reading and by the passing `go build`/`go vet`/`go test ./internal/orchestrator/...` (no regressions, existing `wkspace` tests still green). The resume task-status fix is exercised only indirectly (string-prefix logic, no dedicated unit test either — recommend adding one alongside a future `wkspace`/`worker` resume-path test harness).

## Phase 6: Observability & Tracing (Log & Telemetry)

**Why:**
Running CLI agents as sub-processes (especially in parallel) makes debugging extremely difficult. The MCP JSON-RPC protocol can be easily corrupted by stray standard output logs, and tracking the cost/tokens of the black-box agents requires explicitly capturing structured output.

**Files:**
- `server/cmd/mcp-context/main.go`
- `server/internal/orchestrator/orchestrator.go`
- `server/internal/orchestrator/checkpoint/capture.go`

**Changes:**
- [x] **MCP Server Stdio Redirection:** Was already correct pre-Phase-6 (`cmd/mcp-context/main.go`'s `errLog` always wrote to `os.Stderr`, never `os.Stdout` — confirmed by re-reading the code before touching it). Extended, not fixed: `internal/mcpcontext/logging.go`'s `NewAppLogger(logDir, stderr)` now tees into `<logDir>/mcp-server.log` via `io.MultiWriter` when `logDir` is writable (i.e. the sandbox bind mount from the next item is present), falling back to stderr-only otherwise (e.g. local/non-sandbox runs) — never stdout in either case. Wired into `cmd/mcp-context/main.go` via the new `--log-dir` flag (default `sandbox.LogsContainerDir`, i.e. `/var/log/autocode`).
- [x] **Context Payload Tracing:** `internal/mcpcontext/server.go`'s `Server.SetTrace(w io.Writer)` + `traceRoundTrip` writes one `{"time","request","response"}` JSON line per JSON-RPC round trip (request and response together, not two separately-correlated lines) to any writer; `internal/mcpcontext/logging.go`'s `OpenTraceWriter(logDir)` opens `<logDir>/mcp-trace.jsonl` for append. Gated by `cmd/mcp-context/main.go`'s `--trace` flag or `AUTOCODE_MCP_TRACE=1` env var (spec's "e.g. `--trace` or env var" — implemented both). Best-effort: a trace-write failure logs to the app logger and is otherwise swallowed, never interrupts the JSON-RPC stream.
- [x] **Docker Log Bind-Mount:** `internal/sandbox/sandbox.go` adds `CommandRequest.LogsHostDir` (bind-mounted read-write) and the fixed `sandbox.LogsContainerDir = "/var/log/autocode"` constant; `internal/sandbox/docker.go`'s `Run` mounts it when set (creating the host dir first). Wired from `internal/orchestrator/engine/cli.go`'s `RunCodeStep`: `logsHostDir := filepath.Join(req.HostWorkspace, "logs")` — i.e. `server/.data/workspaces/<task-id>/logs/`, matching `docs/guides/tracing-workflow-logs.md`'s already-documented layout — no new `CodeStepRequest` field needed since it derives purely from the existing `HostWorkspace`. **Not wired into `RunInteractive`** (the browser-terminal session path) — out of scope, that path isn't a CLI-agent run.
- [x] **Real-time Log Streaming:** `internal/sandbox/docker.go`'s `Run` no longer waits for the container to exit before reading logs (the old behavior: `ContainerLogs` without `Follow`, called only after `ContainerWait` returned — meaning a container that never exited cleanly left zero captured output). New `streamContainerLogs` attaches with `Follow:true` immediately after `ContainerStart`, copying via `stdcopy.StdCopy` into `io.MultiWriter(buffer, logFile)` for both stdout/stderr concurrently with `ContainerWait`, so a kill mid-run still leaves a real, up-to-the-point-of-failure log file on disk. `CommandRequest.LogFilePath` carries the target path; `cli.go` sets it to `<logsHostDir>/cli_<step_id>_run.log` (e.g. `cli_cli_implement_frontend_run.log` for the frontend track — StepID-based, not role-based like the spec's illustrative `cli_frontend_run.log`; documented here as the actual naming). Opened `O_APPEND` (not `O_TRUNC`) so a retried step doesn't erase the previous attempt's trace.
- [x] **Telemetry Parsing:** `internal/orchestrator/engine/telemetry.go`'s `parseCLITelemetry` (pure function, unit-tested in `telemetry_test.go`) scans combined subprocess output for the last balanced top-level JSON object and extracts `total_cost_usd`/`cost_usd`, `duration_ms`/`duration_api_ms`, and `tokens_used`/`usage.{input,output,total}_tokens` — tolerant of surrounding non-JSON agent chatter and of CLIs that don't emit any recognized field (`ok=false`, no spurious zero-row). Wired into `engine/cli.go`'s `RunCodeStep` → `CodeStepResult.{TelemetryOK,CostUSD,DurationMS,TokensUsed}` → `cli_spec_step.go`'s `RunCLIStep`, which calls the new `WorkflowRepo.AccumulateJobTelemetry` (additive `gorm.Expr` update, since one `workflow_jobs` row spans every `cli_*` step of a task run) when `TelemetryOK`. New columns via `migration/000023_add_workflow_job_telemetry.{up,down}.sql` (`total_cost_usd float8`, `total_duration_ms`/`total_tokens_used bigint`, all default 0) and `models.WorkflowJob` fields. **`--output-format json` enforced for `claude_code` and `antigravity`** profiles only (`pkg/models/cli_profiles.go`, flag/ordering confirmed against `docs/guides/claude-cli-headless.md` and `antigravity-cli-headless.md`'s own worked examples). **Deviation, left unaddressed:** `openai_codex`'s equivalent flag isn't confirmed in `docs/guides/codex-cli-headless.md` (no `--output-format`/`--json` example there) — rather than guess an unverified flag that could silently break `codex exec`'s existing text-output parsing (auth/quota/loop detection all regex over raw text), left `openai_codex`'s `Args` unchanged. `parseCLITelemetry` will simply find no telemetry (`ok=false`) for codex runs today; needs a live `codex exec --help`/run to confirm the right flag before enabling.

## Phase 7: Resilience & Security (Auth, Cancellation & Smart Timeouts)

**Why:**
Production environments require bulletproof error handling, secure credentials management, and protection against infinite LLM loops without arbitrarily punishing legitimately long-running tasks.

**Files:**
- `server/internal/orchestrator/sandbox/runtime.go` (or wherever subprocess execution lives)
- `server/internal/orchestrator/orchestrator.go`
- `server/internal/workflow/engine.go`

**Changes:**
- [x] **Sandbox Cache Isolation Bug:** Fixed `server/internal/sandbox/docker.go` to mount host caches (`~/.npm`, `~/.cache/pip`, etc.) to `/home/agent/...` instead of `/root/...`, as the sandbox runs under the `agent` (UID 1000) non-root user. The `/root/` mounts were inaccessible and silently breaking dependency caching.
- [x] **Secure Auth Injection:** Audited — already correct pre-Phase-7, verified rather than changed. `internal/orchestrator/engine/cli.go`'s `RunCodeStep` passes `cfg.Env` (which carries `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/etc for `custom`-ref CLI configs) as `sandbox.CommandRequest.Env`, merged by `sandbox.mergedEnv` (`internal/sandbox/sandbox.go:168`) straight into `container.Config.Env` (`internal/sandbox/docker.go` `ContainerCreate` calls) — never interpolated into `req.Command`/the bash script string, so it's invisible to `docker inspect`'s process list and to `CodeStepResult.Command` (which only ever holds `quotedInvocation`, the CLI binary+flags). Deliberately *not* moved to `CommandRequest.SecretEnv`: `internal/sandbox/policy.go:93`'s `validateExecutionPolicy` refuses to start a container that has both `SecretEnv` and network egress enabled, and these CLIs need network access to actually call the provider APIs — `SecretEnv` is for a stricter, network-forbidden class of secret, not provider auth. Leak surface into logs/checkpoints: `internal/orchestrator/llm_trace.go:21` `secretRegexes` (`sk-ant-…`, `sk-…`/`sk-proj-…`, `AIzaSy…`, `ghp_…`/`github_pat_…`) already covers Anthropic/OpenAI/Gemini/GitHub value *shapes* — value-pattern matching rather than env-var-name matching, so it also catches a leaked key printed under a different var name. `redactSecrets` (same file) runs on every `tracker.go:40` `log()` call and on `engine/cli.go`'s `CodeStepResult.Output`/`Command`/`Error` (lines constructing `res` — `redactSecrets(combined)`/`redactSecrets(...Join(quotedInvocation...))`/etc) *before* those ever reach `orchestrator/worker.go:224`'s `o.checkpoint(...)` call (which persists `WorkflowCheckpoint.State`), so checkpoint JSON never carries a raw credential either. New regression test: `internal/orchestrator/redact_secrets_test.go` (`TestRedactSecrets_CoversProviderCredentialFormats`) asserts all four credential shapes are actually caught, not just that the function runs.
- [x] **Context Cancellation (SIGKILL cascade):** The cancel API path already existed pre-Phase-7 (`internal/handler/workflow.go:198` → `Orchestrator.CancelJob` → the `context.CancelFunc` stored per-job in `orchestrator.go`'s `jobCancels`/`queue.go:51`) — what was missing was the last mile: a cancelled `ctx` reaching `internal/sandbox/docker.go`'s `Run` only unblocked its `select` (`case <-ctx.Done(): return nil, ctx.Err()`), relying on the *deferred* `ContainerStop` (SIGTERM, 5s grace, then SIGKILL) to actually stop the container — a real but non-instant cascade. Added an explicit `r.client.ContainerKill(context.Background(), containerID, "SIGKILL")` directly in that `ctx.Done()` branch (`docker.go`, in `Run`) so a cancelled job's container dies immediately instead of after up to 5s of continued (billed) execution; the deferred `ContainerStop`/`ContainerRemove(Force:true)` still run as the cleanup backstop. Not exercised against a live Docker daemon in this session (no daemon available) — the `ctx.Done()` branch itself was already unit-reachable pre-Phase-7 via `StubRuntime`, but `ContainerKill` is Docker-SDK-only and only meaningfully verifiable with a real container.
- [x] **Smart Idle Timeout & Loop Detection:** New `internal/sandbox/activity.go`: `activityWriter` (tracks the unix-nano timestamp of the last byte written) and `lineLoopDetector` (a live, streaming sibling of `engine.loopDetector` — tracks the last 200 non-blank lines in a ring buffer, flags `Detected()` once any single line recurs `loopLineThreshold` (10) times; deliberately broader than `engine.loopDetector`'s error-line-only heuristic, since the goal here is a fast kill switch during the run, not a precise root-cause classifier). Both wrap `docker.go`'s `streamContainerLogs` multiwriter chain (Phase 6) so they observe every byte as it streams, at zero extra I/O cost. `watchForStall` (same file) polls both every 5s and invokes a caller-supplied kill callback with `KillReasonIdleTimeout`/`KillReasonLoopDetected` the first time either trips; wired into `docker.go`'s `Run` as a goroutine started right after `streamContainerLogs`, calling `ContainerKill(...,"SIGKILL")` and recording the reason onto the returned `CommandResult.Killed`/`KillReason` (new fields, `internal/sandbox/sandbox.go`). `CommandRequest.IdleTimeout` (new field, default `sandbox.DefaultIdleTimeout` = 15m when zero) lets a caller override it; `engine/cli.go`'s `RunCodeStep` resolves it via the new `resolveIdleTimeout()`, configurable per-deployment via the `AUTOCODE_CLI_IDLE_TIMEOUT_MINUTES` env var, and threads it into `CodeStepResult.IdleTimeoutHit`/`LoopKilled` (`engine/engine.go`) so a stalled/looping run surfaces a clear `res.Error` ("no stdout/stderr activity for …, killing step as stalled" vs the existing loop message) instead of only failing at the absolute `req.Timeout`. A genuinely active 1.5h run never trips this since every stdout/stderr write resets the idle clock — only *silence* or *exact repetition* kills early. Unit-tested without Docker in `internal/sandbox/activity_test.go` (idle-timeout trigger, loop-detection trigger including a line split across two `Write` calls the way `stdcopy.StdCopy` can chunk mid-line, and a "no false positive on varied output" case) — not exercised against a live Docker daemon/real hung CLI in this session.
- [x] **Partial Retries (Node-level Recovery):** Verified this already works for free via the Phase 5 checkpoint-resume mechanism — no code gap found, so no new code added here. `internal/workflow/step.go:308-310`'s parallel-DAG workflow gives the backend/frontend CLI implement tracks distinct step IDs (`StepCLIImplementBackend`="cli_implement_backend", `StepCLIImplementFrontend`="cli_implement_frontend", both independently `DependsOn: [StepCLISpec]`, `StepMerge` depending on both). `internal/orchestrator/worker.go:356-397`'s resume path lists every checkpoint and seeds `engine.CompletedSteps[cp.Step]` for each one whose `state["status"] == StepStatusSuccess`, *except* for two exact-string special cases (`worker.go:380-385`) that only strip checkpoints when `job.Step == workflow.StepCLIImplement` (the legacy single-track step ID, "cli_implement") — which never matches when the workflow in progress is the parallel-track one (`job.Step` would be "cli_implement_backend"/"cli_implement_frontend" instead), so that exclusion is a no-op here and a successful backend-track checkpoint survives untouched into `CompletedSteps` on retry while a failed/absent frontend-track checkpoint does not, causing `internal/workflow/engine.go`'s DAG executor to skip re-running backend and only respawn frontend. No test added for this specific scenario — the seeding logic lives inline inside `worker.go`'s large job-execution function (no full orchestrator mock harness exists in this repo for it, unlike the smaller pure-logic pieces above), so exercising it end-to-end would need either a heavier integration harness or a live DB; left as verified-by-code-reading with the file:line trail above rather than adding a new large mock scaffold for one code path with no behavior change.
